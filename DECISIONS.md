# Decision log

One line per decision: what you chose and why. This becomes your interview prep and your case study.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-10-04 | Split train, validation, and test by time, not randomly | A random split lets the model learn from future transactions, which inflates results |
| 2026-10-04 | Excluded gender, date of birth, and age from features | Protected attributes shouldn't drive financial decisions, and the model should work without them |
| 2026-10-04 | Use DuckDB for analysis in Weeks 1–2 and Supabase Postgres only for the Week 3 app | 1.85M rows would likely exceed Supabase's free tier; DuckDB is a local file built for fast analytical queries, while Postgres suits the app's small reads and writes |
| 2026-10-04 | Use the Kaggle Sparkov dataset (kartik2112/fraud-detection): 1,852,394 transactions, 9,651 fraud (0.521%), 2019-01-01 to 2020-12-31 | Only well-known public card-fraud dataset with real timestamps, card IDs, locations and merchant categories, which our features need; it is simulated, so results say nothing about real banks |
| 2026-10-04 | Combine Kaggle's two files and re-split by month ourselves | The given files have no validation set, split mid-day on 2020-06-21, and per-card history features need all of a card's past transactions in one table |
| 2026-10-04 | Train Jan 2019–Jun 2020, tune Jul–Aug 2020, calibrate Sep 2020, test Oct–Dec 2020 (dates in config.yaml) | 18 months to learn from, 2 to tune, 1 to calibrate, 3 untouched; fixed before looking at patterns so the test months stay unseen. Test fraud rate is lower (Dec 2020 is 0.19%) because December volume doubles while fraud doesn't |
| 2026-10-04 | Feature pattern 1: amount. $500+ transactions are fraud 23% of the time vs 0.15% under $100 | Fraudsters go for large sums, so the amount, and especially the amount compared with that card's usual spend, should be the strongest signal |
| 2026-10-04 | Feature pattern 2: hour of day. 22:00–03:59 has 1.4–2.8% fraud vs about 0.1% the rest of the day | Fraud clusters at night, plausibly when cardholders are asleep and slower to notice; hour is cheap to compute and has no leakage risk |
| 2026-10-04 | Feature pattern 3: category. Online shopping, online misc and grocery POS run 1.3–1.7% fraud vs about 0.2% elsewhere | Card-not-present (online) purchases are easier to commit with stolen card details; category tells the model which merchants carry that risk |
| 2026-10-04 | Historical features use only transactions strictly earlier in time (windows end 1 microsecond before now), proven by a test that adding a later transaction changes no earlier feature | 44 card/second ties exist; a row-based window would let one of each tied pair see the other, a subtle leak. The test fails if any window looks forward |
| 2026-10-04 | Amount ratio uses the median of all the card's earlier amounts; raw amount is also a feature | Median ignores one-off big purchases better than the mean. Raw amount covers a card's first transaction, where there's no history. On real data the typical (median) ratio is 8.7 for fraud vs 1.0 for legitimate |
| 2026-10-04 | Kept distance_km even though fraud and legitimate both average about 76 km | It shows no signal in this simulated data, but it's cheap and the model can decide; we'll check its importance in step 6 |
| 2026-10-04 | Kept 3 months before test (Jul–Sep 2020) and 3 test months (Oct–Dec 2020) rather than 2 + 2 | Gives 1,076 pre-test and 936 test fraud cases instead of 724 and 552, so metrics are steadier; a 2-month test would be only Nov–Dec, the two most unusual months |
| 2026-10-04 | Baseline: logistic regression with log-scaled amount and ratio, missing-ratio flag, and one-hot category, hour and day of week; no class weighting | Log stops $28k transactions swamping the scale; one-hot hour lets a linear model learn the night peak; no weighting keeps probabilities honest for calibration. Test: PR-AUC 0.376, ROC AUC 0.910, 59.8% of fraud caught reviewing the top 1% |
| 2026-10-04 | Lead with PR-AUC and recall at top 1%, not accuracy | Always predicting "not fraud" is 99.67% accurate on test and catches nothing; ROC AUC also looks flattering when fraud is rare |
| 2026-10-04 | LightGBM handles imbalance with scale_pos_weight = 13 (about the square root of the 173:1 legit-to-fraud ratio), chosen automatically in train.py from the candidates in config.yaml | On the tuning months it beat no weighting (PR-AUC 0.815) and full balancing at 173 (0.815) with 0.823. It roughly doubles predicted probabilities, which step 7's calibration will correct |
| 2026-10-04 | Early stopping on tuning-month PR-AUC (stop after 100 trees without gain); test months never touch training | Picks the number of trees (659) without guessing; using test for this would leak test information into the model, so LightGBM's tuning scores are slightly optimistic and only test is reported as the result |
| 2026-10-04 | LightGBM beats the baseline: test PR-AUC 0.838 vs 0.376, 93.3% vs 59.8% of fraud caught reviewing the top 1% | Trees capture thresholds and interactions (large amount at night in an online category) that a linear model can't. Precision at top 1% is 31.0% against a ceiling of 33.2% (936 frauds in 2,816 reviewed slots) |
| 2026-10-04 | Feature importance (gain): amount 68%, category 15%, hour 10%; amount-to-median ratio only 3% | Ratio overlaps with raw amount, which the model uses first; distance (0.7%) confirms step 4's suspicion that it carries no signal in this simulated data |
| 2026-10-04 | Split the Jul–Sep 2020 months into tuning (Jul–Aug) and calibration (Sep) | The same months were choosing the class weight, choosing the number of trees, and about to fit calibration; calibration on months that tuned the model would look better than it is. After retraining on tuning months only, the same weight (13) won and test results barely moved: PR-AUC 0.8376 to 0.8376, recall at top 1% 93.4% to 93.3% (one fewer fraud caught) |
| 2026-10-04 | Daily review budget 30 (was 200), an assumption | Test months average about 3,060 transactions and 10 frauds a day. A budget of 200 is 20x daily fraud, so every policy could review everything mildly suspicious and the comparison would measure nothing. 30 is about 1% of volume, matching the recall-at-top-1% metric, and forces a choice about which cases deserve an analyst |
| 2026-10-04 | Audit: Oct–Dec 2020 is used only for final scoring | Models, imputer, scaler, category list, class weight and tree count all come from train or tuning months. Features span all months but only look backward (leak test). Disclosure: the step 3 monthly chart displays test-month fraud rates, and choosing 3 + 3 over 2 + 2 looked at test-period fraud counts; neither fed into features or model settings |
